# Архитектура панели «Доступ»

## Владение маршрутом

Интеграция регистрирует только `dashboard-access-v1`. Перед регистрацией выполняется проверка существующего владельца. Идентификатор создавшей маршрут config entry сохраняется в `hass.data`; при выгрузке удалить маршрут может только эта же запись.

Статический каталог frontend регистрируется отдельно. Параметр версии в `module_url` обеспечивает cache-busting без цепочки исторических bundle-файлов.

## Поток состояния

1. Home Assistant передаёт новый объект `hass` в web component.
2. Обновление объединяется через `requestAnimationFrame`.
3. Меняются только текст, иконка, цветовой класс и доступность командных кнопок.
4. Постоянные Header, рабочая область, карточки и нижнее меню не перестраиваются.

Физическое положение секционных ворот вычисляется отдельной чистой функцией только из `binary_sensor.sensor_do_zb_15_16_contact`. Состояния обоих `cover` допускаются только для оценки доступности канала управления.

## Поток команды

1. Нажатие выбирает одну из шести заранее разрешённых команд.
2. Проверяется доступность канала управления.
3. Показывается подтверждение с объектом и действием.
4. После подтверждения ставится общий lock и отметка времени дедупликации.
5. Вызывается только `hass.callService("cover", service, {entity_id})`.
6. Успешный вызов показывает сообщение об отправке, но не меняет положение.
7. Ошибка сохраняется в постоянной плашке до явного закрытия пользователем.

## Будущий домофон

- `frontend/src/data/intercom.js` — возможности и будущие подтверждённые сущности;
- `frontend/src/views/intercom-view.js` — отдельное представление;
- `INTERCOM_MODULE.enabled` — явный флаг допуска в интерфейс.

До модернизации `enabled` равен `false`, а `entityIds` остаётся пустым объектом. Планируемые возможности: связь, вызов, камера, открытие калитки или двери и история событий.
